Feature List:
PFin-Dash is a Personal Finance Dashboard with the following features. Status markers reflect the actual code, not the aspiration — check them before assuming a feature is wired end-to-end.

1. Mutual Funds — DONE (backend + UI fully wired)
    - Upload CAMS CAS detailed statement (PDF, password-protected supported). This is the source of information.
    - Get/Refresh NAV for the funds held (via api.mfapi.in, keyed by AMFI code).
    - Show Holding statement with Gains and XIRR% (tree: scheme -> folio).
    - Edit Folio names to give them human readable nicknames.
    - On double click of a holding statement line, show Transaction statement for the selected MF Scheme/Folio.
    - Delete a single transaction row from the transaction statement view (recomputes residual units and XIRR for the remaining rows).

2. Equity Stocks — DONE (backend + UI fully wired)
    - Upload CSV file having the details of equity transactions (columns: Transaction ID, NSE Symbol, Demat AC, Transaction Date, Transaction Type, Units, Price per Unit, Expense per Unit — see `data/equity_transactions.csv` for a sample).
    - Get / Refresh Last Traded Stock Price using Yahoo Finance (yfinance, NSE tickers via the `.NS` suffix).
    - Show Equity Holding statement with Gains and XIRR% (tree: symbol -> demat account).
    - On double click of a holding statement line, show Transaction statement for the associated stock name / demat account.
    - Delete a single transaction row from the transaction statement view (recomputes residual units and XIRR for the remaining rows).

3. NPS — DONE (backend + UI fully wired)
    - Upload NPS Transaction statements from Protean (CRA) — the upload modal accepts multiple CSV files at once (see `data/nps/*.csv` for samples: one file per PRAN per year, Tier I and Tier II are separate files).
    - Get / Refresh NAV via the npsnav.in API (`https://npsnav.in/api/detailed/<SchemeID>`), resolving each scheme name found in the uploaded statements to a SchemeID via `nps_scheme_master` (see below).
    - Show holding statement with Gains and XIRR% (tree: scheme -> PRAN).
    - On double click of a holding statement line, show Transaction statement for the associated fund and scheme.
    - No delete-transaction feature for NPS yet (unlike MF/Equity) — wasn't part of this pass; would follow the same pattern if wanted later.

Implementation status detail:

- `compute/mf_functions.py` + `compute/db_duckdb.py`: fully implemented — PDF parsing (casparser), DuckDB upsert/query, async NAV refresh, XIRR at scheme-folio/scheme/total levels, holdings tree build, folio renaming, single-transaction deletion (`delete_transaction()`, keyed by the same composite key used to de-dupe on insert — `isin`+`folio`+`txn_date`+`type`+`units`+`balance` — plus `txn_id` to disambiguate exact duplicates). Originally built on Delta Lake (`compute/db_deltalake.py`) as an experiment; migrated to DuckDB for consistency with Equity/NPS. The migration copied all 4 tables (1411 transactions, 17 NAVs, 41 XIRR rows, 18 folios in the data available at migration time) straight across via `pl.read_delta()` -> `INSERT ... BY NAME`, verified against a pre-migration snapshot (grand totals, XIRR, and all 17 scheme rows matched to within float rounding). The old `data/delta` directory was left on disk untouched as a backup rather than deleted — safe to remove once you've confirmed the DuckDB data looks right.
- `compute/eq_functions.py` + `compute/db_duckdb.py`: fully implemented — CSV ingestion into DuckDB `equity_trans`, residual-units computation (FIFO-style, recomputed over the whole table on every ingest/delete so incremental uploads and deletions stay correct), LTP refresh into `equity_master` via yfinance, XIRR at symbol-demat/symbol/total levels persisted to `equity_xirr`, live holdings-tree build, transaction lookup by stock/demat pattern, and single-transaction deletion (`delete_equity_transaction()`, keyed by `trans_id` since it's already a stable primary key). `get_equity_prices()` had a real bug — `str.strip_chars_end(".NS")` strips a *character set*, not the literal suffix, so tickers ending in N/S/. (e.g. `TCS` -> `TC`, `SBIN` -> `SBI`) were silently corrupted; fixed to `str.strip_suffix(".NS")`.
  - `equity_name` in `equity_master` currently just mirrors the ticker symbol (no company-name lookup); there's no equity/stock rename UI yet analogous to MF folio renaming, though the schema and refresh logic (LTP refresh never overwrites `equity_name`) already support adding one.
  - Cost basis for XIRR/invested-amount ignores `expense_per_unit` (mirrors how MF ignores fees in `nav*residual_units`); charges/net_amount are only computed for the transactions-modal display, not for XIRR.
  - Both transaction tables' delete flows recompute residual units for the *entire* table (not just the affected folio/symbol), since a deleted purchase row shifts FIFO consumption for everything downstream of it in that folio/isin (MF) or symbol/demat (Equity) stream.
- `compute/nps_functions.py`: fully implemented, mirroring the Equity module's live-computation pattern. Key pieces:
  - `_parse_nps_statement()` parses Protean's wide-format CSV (fixed header/summary blocks, then a "Transaction Details" table with `Date, Particulars, [Withdrawal col], {scheme} Amount/NAV/Units` repeated per scheme). Scheme columns are located by scanning for headers ending in `Amount (Rs)` rather than a fixed column offset — one real sample file (`110037291972_2017.csv`) omits the "Withdrawal/deduction..." column that the others have, which shifts every scheme column left by one; a fixed offset silently mis-parsed the NAV column's header text as a second, bogus "scheme". "Opening balance"/"Closing Balance" rows are skipped (not real transactions); negative amounts/units are written in parens (`(20.35)`) and parsed accordingly; NAV is always plain positive.
  - `ingest_nps_transactions()` upserts into `nps_trans`, keyed by `pran`+`scheme`+`txn_date`+`description`+`units` (no synthetic per-row ID needed - realistically at most one row per scheme per date per statement), then `_recompute_nps_derived()` recomputes running `balance` (plain cumulative units) and `residual_units` (same FIFO-style formula as MF/Equity) over the whole table.
  - `ingest_nps_scheme_master()` parses the tab-separated npsnav.in "daily NAV data" export (despite its `.xls` extension) into `nps_scheme_master` (SchemeID -> PFM/scheme name/NAV snapshot). This was loaded once from the user-provided `data/nps/daily_nav_data_1785919627.xls` (263 schemes); there's no UI to re-upload it — call `ingest_nps_scheme_master()` directly (or ask for it to be re-run) if npsnav.in's scheme list changes. Not exposed via `api.py` or the UI, unlike the other ingest functions, since it wasn't part of the original NPS feature list.
  - `_match_scheme_id()` resolves a raw scheme name from a Protean statement (e.g. `"NPS TRUST- A/C HDFC PENSION FUND MANAGEMENT LIMITED SCHEME E - TIER I"`) to a `nps_scheme_master.scheme_id`, because the three sources (Protean statement text, npsnav.in's own scheme names, and the mapping file's names) all spell the same scheme differently. It matches on (tier I/II, scheme letter E/C/G/A) plus brand-word overlap after stripping boilerplate tokens (NPS/TRUST/PENSION/FUND/MANAGEMENT/etc.), then prefers the `DIRECT` channel variant over the plain/POP variant over the `GS` (government-sector) variant when several candidates tie, since contributions in the sample data come via eNPS/Direct. Returns `None` (no crash, no NAV for that scheme) if nothing matches - special/rare scheme types (Tax Saver, Vatsalya, Sanchay, etc. that don't fit the E/C/G/A pattern) aren't specifically handled.
  - `refresh_nps_nav()` fetches `https://npsnav.in/api/detailed/<SchemeID>` concurrently (httpx async, mirroring MF's NAV-refresh pattern) for every resolved scheme and upserts into `nps_master` (keyed by the raw scheme name, mirroring `equity_master`).
  - `compute_nps_xirr()` / `get_nps_holdings()` / `get_nps_transactions()` mirror the equivalent Equity functions exactly (scheme-pran/scheme/total XIRR levels; live scheme -> PRAN holdings tree; ILIKE-pattern transaction lookup).
  - Known data caveat found while testing against the real sample files: PRAN `110037291972`'s Tier I scheme changed from SBI to HDFC at some point, and the SBI statement covering that transition wasn't among the uploaded files, so there's no explicit transfer-out transaction. The result is both the old SBI scheme and the new HDFC scheme show up as separate holdings with real balances, double-counting what is presumably now a single corpus. This isn't a parsing bug — it's exactly what the uploaded statements say — but it means the current total is likely overstated until/unless the missing transfer statement is uploaded.
- `api.py`: exposes MF methods (`mf_get_holdings`, `mf_refresh_nav_xirr`, `mf_process_cas_pdf`, `mf_get_transactions`, `mf_get_folio_list`, `mf_update_folio_name`, `mf_delete_transaction`), Equity methods (`eq_get_holdings`, `eq_refresh_ltp`, `eq_process_transactions_csv`, `eq_get_transactions`, `eq_delete_transaction`), and NPS methods (`nps_get_holdings`, `nps_refresh_nav`, `nps_process_transactions_csv`, `nps_get_transactions`).
- `ui/src/services/api.ts`: the MF, Equity, and NPS functions all call the real pywebview bridge (`window.pywebview.api`) and are declared in `REQUIRED_API_METHODS`. No dummy data remains in this file.

Fixed: all three holdings pages (`mf_holdings_page.svelte`, `equity_holdings_page.svelte`, `nps_holdings_page.svelte`) used to call `table.setColumns()`/`setData()` from their `$effect` as soon as `table` was truthy, with no guard for whether Tabulator's async internal init had actually finished — Tabulator's constructor returns before its DOM build completes, so an effect re-run in that window threw "Cannot read properties of null (reading 'firstChild')". This only surfaced visibly on `nps_holdings_page.svelte` while it still returned near-instant dummy data; wiring NPS to the real async backend hid the symptom without fixing the underlying race. All three pages now gate post-init updates behind a `tableReady` promise resolved by Tabulator's one-time `tableBuilt` event (see `applyPayload()` in each page) instead of relying on timing. Verified the fix against the exact original failure mode (calling setColumns/setData synchronously right after construction, worst case) via a standalone repro in the browser: the old pattern throws the same error, the gated pattern doesn't.

Technical Architecture:

UI built using Svelte (Vite) and shown using Pywebview (main.py). All computations and business logic is in Python; the UI only calls into `window.pywebview.api` (wrapped by `ui/src/services/api.ts`) and never talks to storage directly.

Folders
- `ui` — Svelte frontend source (`ui/src`), built to `ui/dist` (what `main.py` actually loads — run `npm run build` in `ui/` after frontend changes, since pywebview serves the static build, not the Vite dev server).
  - `ui/src/components/mutual_fund`, `ui/src/components/equity`, `ui/src/components/nps` — one holdings page + transactions modal + upload modal per asset class.
  - `ui/src/services/api.ts` — single point of contact for all Python calls.
- `compute` — Python business logic. One module per asset class (`mf_functions.py`, `eq_functions.py`, `nps_functions.py`, all done), plus `db_duckdb.py` (the single DuckDB connection + schema helper shared by all three - MF used to have its own separate Delta Lake helper, `db_deltalake.py`, now removed).
- `data/PFin.duckdb` — the one DuckDB database for all asset classes. Schema is created/reconciled on demand by `compute/db_duckdb.py:ensure_schema()` (called from `get_connection()`), so a fresh DB file works out of the box.
  - MF tables: `mf_transactions` (keyed by `isin`+`folio`+`txn_date`+`type`+`units`+`balance`), `mf_nav` (per-AMFI NAV cache, keyed by `amfi`; has a `"1d_change"` column that needs quoting in SQL since it starts with a digit), `mf_xirr` (XIRR at scheme-folio/scheme/total levels), `mf_folios` (folio -> friendly-name mapping for the rename feature).
  - Equity tables: `equity_trans` (transactions, keyed by `trans_id`), `equity_master` (per-symbol LTP cache + name), `equity_xirr` (XIRR at symbol-demat/symbol/total levels, mirrors `mf_xirr`). Holdings are computed live from these three, not persisted — same pattern as `get_mf_holdings()`. An earlier scaffold table `equity_holdings` (symbol+demat_ac with invested/current/xirr columns but no units or price) was dropped by `ensure_schema()` since it was unused and structurally couldn't hold what the UI needs.
  - NPS tables: `nps_trans` (transactions, keyed by pran+scheme+txn_date+description+units), `nps_scheme_master` (the npsnav.in SchemeName -> SchemeID reference data), `nps_master` (per-scheme current NAV cache, keyed by the raw scheme name to match `nps_trans.scheme`), `nps_xirr` (XIRR at scheme-pran/scheme/total levels). Holdings computed live, same pattern as Equity.
- `data/delta` — leftover from the pre-migration Delta Lake storage. No longer read by any code; kept on disk only as a backup of the pre-migration MF data. Safe to delete once you've confirmed the migrated DuckDB data looks right.
- `data/equity_transactions.csv` — sample equity transactions CSV used for development/testing.
- `data/nps` — sample Protean NPS transaction CSVs (one per PRAN per year; `*_TierII_*` files are Tier II) plus `daily_nav_data_1785919627.xls` (actually tab-separated text, the npsnav.in SchemeID mapping export used to seed `nps_scheme_master`).
- `api.py` — Python API surface exposed to the UI via pywebview's `js_api`. MF, Equity, and NPS methods all implemented.
- `main.py` — pywebview entry point; creates the window pointing at `ui/dist/index.html` with `js_api=Api()`.
